# 站点登录状态与密钥备份

pt-tools 用你配置的 Cookie 或 API Key 定时访问站点的个人信息，读取站点提供的 `last_access` / `last_login`，算出距离不活跃封号还剩几天，快到期限时通过已配置的通知通道提醒。Cookie 可以用 PT Tools Helper 同步。

## 使用流程

1. 在站点 → 站点列表中启用目标站点，并配置好认证信息。Cookie 认证的站点可以安装 [PT Tools Helper](browser-extension.md)，在浏览器中登录站点后一键同步 Cookie；API Key 和 Passkey 站点在 Web UI 中手动填写。
2. 站点列表的「剩余天数」列显示距离封号阈值还有几天，负数表示已经超过阈值；「判定活跃」列（默认隐藏，可在「列设置」里打开）是用于提醒判定的活跃时间，规则见[判定活跃](#判定活跃)。鼠标悬停「剩余天数」或「判定活跃」可以看到判定依据、下次探测时间和连续失败的开始时间，悬停「状态」可以看到最近一次没有成功的探测结果。
3. 点击行内的「保号配置」按钮，按站点设置封号判定天数、提前提醒天数、提醒 cron、通知通道和探测模式。
4. 行内的「立即探测」按钮马上探测一次登录状态，「测试提醒」按钮向通知通道发送一条测试消息；列表上方的「探测已启用」对所有已启用站点各探测一次，最多 3 个并发。
5. 收到提醒后正常访问站点。Cookie 失效时重新同步，再点「立即探测」确认状态已经刷新。

站点详情页的「保号规则」卡片也显示探测结果、判定依据、下次探测时间、连续失败的开始时间和访问状态。

> [!NOTE]
> 探测能刷新多数站点的 `last_access`（最近动向）。少数站点按 `last_login`（实际登录）或做种活跃度判断是否清理账号，这类站点仍需定期手动登录，不能只看剩余天数。

## 每站点配置

「保号配置」对话框中的各项：

| 配置项       | 默认值          | 说明                                                               |
| ------------ | --------------- | ------------------------------------------------------------------ |
| 封号判定天数 | `30`            | 不活跃超过这个天数，站点就可能封号                                 |
| 提前提醒天数 | `10`            | 距离封号还剩多少天开始提醒                                         |
| 提醒 cron    | `0 10,22 * * *` | 标准 5 字段 cron（分 时 日 月 周），默认每天 `10:00` 与 `22:00`    |
| 通知通道     | 空              | 选择后只发送到选中且已启用的通道；留空则发送到所有已启用通道       |
| 探测模式     | 自动            | 自动：跟随定时探测；手动：只在点击「立即探测」时执行；禁用：不探测 |

## 定时探测

探测模式为「自动」的已启用站点由后台定时探测：

- 后台每分钟检查一次，逐个探测到了时间的站点。
- 每个站点有一个固定的随机偏移，在 1 秒到 6 小时之间。升级后的老站点和新加的站点按这个偏移安排第一次探测，所以第一轮分散在 6 小时内完成。重启不会让所有站点重新探测一遍，没到时间的站点照常等待。
- 每次探测之后，按结果安排下一次：

| 本次结果                                               | 下次探测                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 正常                                                   | 约 6 小时后（上下浮动 10%）                                                    |
| 会话已过期、密钥错误                                   | 24 小时后，失效的凭证不必频繁请求站点                                          |
| 被反爬拦截、网络错误、请求过于频繁、解析失败、未知状态 | 连续第 1、2、3 次失败后分别隔 1、2、4 小时，之后每 6 小时                      |
| 未配置凭证                                             | 不请求站点；6 小时后在本地检查凭证是否已经补上，补上后也可以直接点「立即探测」 |
| 暂不支持探测                                           | 不请求站点；24 小时后再检查一次                                                |

「立即探测」不受这张表限制，执行后按本次结果重新安排下一次。

单次探测最多 150 秒，其中向站点发出的请求最多 60 秒。超时按失败记录，不影响其他站点的探测。

探测前先做两项不发请求的检查：

- 站点没有内置定义（不在[支持站点](../sites.md)列表中，例如通过接口或模板导入添加的动态站点）时，状态记为「暂不支持探测」。
- 缺少认证方式要求的凭证时，状态记为「未配置凭证」：Cookie 认证需要 Cookie，API Key 认证需要 API Key，Cookie + API Key 认证两者都要，Passkey 认证需要 Passkey。

这两种状态不请求站点、不计入连续失败，也不发失败提醒。

## 判定活跃

「判定活跃」是剩余天数和封号提醒依据的时间：

- 最近一次探测正常时，用站点返回的最近访问时间（`last_access`）；站点不提供时，用站点返回的最近登录时间。
- 最近一次探测没有成功（或者还没有探测过）时，站点数据可能已经过时，再与浏览器扩展记录的访问时间比较，取较新的一个。所以探测出问题期间，你用浏览器正常访问站点，剩余天数不会照样减少。
- 浏览器扩展在你打开站点页面时上报访问时间，同步 Cookie 时也会附带；这个时间只会前进，不会被较早的上报覆盖。

判定依据显示为「站点最近访问」「站点最近登录」或「浏览器访问」。

如果探测正常，但站点返回的最近访问时间与上次相同，并且已经是 48 小时以前，说明自动探测没有刷新这个站点的访问时间。站点列表在「剩余天数」旁标出「访问未生效」，封号提醒的正文也会加上一句提示。这类站点需要你手动登录访问；站点的最近访问时间前进后，标记自动消失。

## 提醒

### 封号提醒

剩余天数不超过「提前提醒天数」后开始提醒：

- 按「提醒 cron」的时间发送，同一个 cron 时段只发一次。
- 剩余天数降到比上一次提醒更紧急的档位（14、7、3、1 天）时，立即补发一次，不等 cron。
- 提醒正文包含上次活跃时间、判定依据和剩余天数。

### 探测失败与恢复提醒

| 情况                                                   | 什么时候提醒                                                                 |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 会话已过期、密钥错误                                   | 发现后的下一次检查（每分钟一次）就提醒；没有恢复时，每 24 小时至多再提醒一次 |
| 被反爬拦截、网络错误、请求过于频繁、解析失败、未知状态 | 从第一次失败起持续满 24 小时后提醒；之后每 24 小时至多一次                   |
| 未配置凭证、暂不支持探测                               | 不提醒                                                                       |
| 恢复正常                                               | 发过失败提醒的站点，探测恢复正常后提醒一次                                   |

### 通知通道与静默时段

- 提醒发到「保号配置」里选中且已启用的通道；没有选择时，发到提醒产生时所有已启用的通道。
- 静默时段按通道各自生效，设置位置与 RSS 通知相同，见[RSS 上新通知的静默时段](chatops-rss-notify.md#静默时段)。处在静默时段的通道等静默结束再发，其他通道照常发送。
- 剩余 1 天以内（含已超过阈值）的封号提醒和「测试提醒」不受静默时段限制。
- 发送失败时分别在 1、5、30 分钟后重试，第 4 次仍失败就放弃；重试时间落在静默时段内也会等到静默结束。
- 提醒经 ChatOps 已连接的通道发送，QQ、Telegram 不会另起连接。通知服务没有启动时（日志里有相应告警），提醒只记录、不发送。

## 备份加密密钥

`~/.pt-tools/secret.key` 用于 AES-256-GCM 加密站点 Cookie 等凭证。密钥丢失后，已存储凭证无法解密，只能重新同步。

导出备份：

```bash
pt-tools secret export > ~/secret.key.backup
chmod 600 ~/secret.key.backup
```

恢复备份：

```bash
pt-tools secret import --force < ~/secret.key.backup
```

> [!CAUTION]
> 密钥备份具备与原始密钥相同的敏感性。请存入密码管理器、加密介质或受控备份系统，不要提交到代码仓库或明文云盘。

### Docker 持久化

容器部署必须把 `/app/.pt-tools` 挂载到宿主机或受管卷。该目录同时包含 `secret.key`、数据库、日志和临时种子文件；重建容器前应确认挂载存在且备份可用。

```yaml
volumes:
  - ./data:/app/.pt-tools
```

删除 `./data` 会同时丢失数据库与密钥。备份时请把密钥与数据库作为一个一致性单元保存。

## 合规边界

此功能使用用户自己的 Cookie 或 API Key 周期访问站点页面或 profile API。启用前请确认站点规则允许自动化访问，并根据个人风险偏好设置探测频率：

- 部分站点可能把频繁脚本访问视为违规。
- 登录状态字段由站点提供，可能缺失、延迟或语义不同。
- pt-tools 不保证该功能可以避免封号，也不承担因自动化访问导致的警告、降级或封禁。

认证信息获取与同步方法见[获取 Cookie / API Key](get-cookie-apikey.md)。
